The models and techniques, in plain English

Read this section first — every module below refers back to these.

Ordinal classification

A classification problem where the categories have a meaningful ORDER. Here: Normal < Mild AMS < Severe AMS < HAPE risk < HACE risk. Being one tier off should count as a smaller mistake than being four tiers off — plain multi-class classification can't express that.

XGBoost, trained as a regressor

The selected model. Instead of classifying into 5 discrete categories, it's trained to predict the severity INDEX as a continuous number (0.0-4.0). Predicting 3.7 for a true 4 is a small loss; predicting 0.2 is a big one — the loss function itself understands tier ordering.

LSTM (comparison model)

A small recurrent neural network trained on raw 60-second vitals windows, testing whether a model can learn temporal patterns directly from a sequence, without a human hand-engineering a "trend" feature first. Built honestly, not built to lose — but it lost on the metric that matters.

Mean Absolute Tier Error (MATE)

The metric models are actually selected by: average |predicted tier − true tier|. Directly measures "how clinically costly are this model's mistakes," which plain accuracy can't.

Hysteresis gate

The logic deciding whether a classification actually triggers an alert: severity must stay at/above a threshold for 3 consecutive readings (any dip resets it) AND 15 minutes must have passed since the last alert.

DataSource interface

An abstract two-method contract (next_reading(), reset()) every reading source implements — this is what makes a future real-hardware phase a drop-in swap instead of a rewrite.

1The sigmoid onset curve

Symptoms ramp in gradually over minutes — never an instant jump — because a model trained on step-function data would learn to detect abrupt discontinuities, not the gradual real-world deterioration this system needs to catch.

def _smooth_ramp(n_samples, onset_fraction, rng):
    onset_start = int(n_samples * onset_fraction)
    t = np.arange(n_samples, dtype=float)
    remaining = max(n_samples - onset_start, 1)
    center = onset_start + remaining * 0.5
    width = max(remaining * 0.18, 1.0)
    ramp = 1.0 / (1.0 + np.exp(-(t - center) / width))
    ramp[t < onset_start] = 0.0
    return ramp
2Per-tier physiological profiles

Each tier has RANGES, not fixed numbers, so within-class variation is natural rather than every "Mild AMS" case looking identical.

TIER_PROFILES = {
    "Normal":     TierProfile((-1.5, 1.5),  (-5, 8),   (-0.2, 0.2), progressive=False),
    "Mild AMS":   TierProfile((4, 8),       (10, 20),  (-0.1, 0.4), progressive=False),
    "Severe AMS": TierProfile((8, 14),      (20, 35),  (0.0, 0.6),  progressive=False),
    "HAPE risk":  TierProfile((14, 22),     (28, 45),  (-0.1, 0.5), progressive=True),
    "HACE risk":  TierProfile((16, 26),     (32, 50),  (-0.1, 0.7), progressive=True),
}
Why "progressive": Mild/Severe AMS plateau after onset (sick but stable); HAPE/HACE risk keep worsening through the whole window (no recovery) — matching the clinical idea that these are decompensating states, per docs/lls_mapping.md.

def generate_dataset(n_subjects=400, duration_minutes=90, seed=RANDOM_SEED):

harespod_loader.py

Day 1, rewritten in a later session

Loads real ambient-air hypobaric chamber data — written speculatively before download, then rewritten once the real files could be inspected.

Requiresdata/raw/harespod/ (manual Figshare download)
1Column mapping — confirmed from the actual device driver

The raw CSVs are headerless numbers. The real column meaning was only confirmed by reading the BerryMed PM6100 device driver source shipped alongside the data.

# spv -> m_SPO2Sat    (SpO2 Saturation, the real percentage — used as spo2)
# hr  -> m_HeartRate   (used directly as hr)
# spo -> SPO2 Wave     (raw PLETHYSMOGRAPH waveform, NOT a percentage — unused)
What could have gone wrong: the file named spo superficially looks like it could be "SpO2," but it's a raw waveform on a completely different scale. Using it directly would have silently produced nonsense.
2The rescale — first attempt, and the bug it produced
# FIRST attempt: rescale onto the device's documented raw range
SPO2_DEVICE_RANGE = (0.0, 100.0)
HEART_RATE_DEVICE_RANGE = (0.0, 250.0)
Bug found: this produced a subject with a 174bpm average RESTING heart rate — physiologically implausible. The device range describes what the sensor CAN report, not what any real subject's session spanned (their true min/max was compressed into [0,1] by per-subject normalization, with the original scale unrecoverable).
SPO2_DEVICE_RANGE = (70.0, 100.0)          # FIX: physiological range instead
HEART_RATE_DEVICE_RANGE = (40.0, 160.0)
Fix: rescale onto a physiologically-plausible range instead — still an approximation, documented explicitly as such in the code, but produces numbers a real pulse oximeter would plausibly report.
3The GMT offset bug

6 of 15 subjects had their key_timestamp.txt altitude markers recorded exactly 8 hours ahead of their own vitals data.

data_start = pd.to_datetime(timestamps).min()
offset_hours = (marker_times[0] - data_start).total_seconds() / 3600
if abs(offset_hours - 8) < 0.1:
    marker_times = marker_times - pd.Timedelta(hours=8)
elif abs(offset_hours) > 0.1:
    raise ValueError(f"{subject_dir}: unexpected {offset_hours:.2f}h offset")
Unfixed impact: the interpolation markers would never overlap the actual data timeline, silently producing a CONSTANT altitude for the whole recording instead of a real ascent profile.
Fix: detected per-subject by comparing the first marker's time to the data's own minimum timestamp; corrected before interpolating. Two further per-subject exceptions handled explicitly: subject 314c's first marker read "Start to Rec" instead of a number; subject 328a's protocol never reached 4000m (that marker is dropped, not faked).

rule_baseline.py

Day 4

The sanity floor every ML model must clearly beat — hand-written if/else, no learned parameters.

1The cascading thresholds
def classify_row(spo2_delta, hr, spo2_trend_5min):
    hr_elevation = hr - hr_normal_mid
    steep_negative_trend = spo2_trend_5min < -0.15

    if spo2_delta >= 16 or (spo2_delta >= 10 and steep_negative_trend):
        if spo2_delta >= 20 and hr_elevation >= 35:
            return SEVERITY_INDEX["HACE risk"]
        return SEVERITY_INDEX["HAPE risk"]
    if spo2_delta >= 8 or hr_elevation >= 20:
        return SEVERITY_INDEX["Severe AMS"]
    if spo2_delta >= 4 or hr_elevation >= 10:
        return SEVERITY_INDEX["Mild AMS"]
    return SEVERITY_INDEX["Normal"]
Also reused directly to LABEL the real (Harespod) data post-hoc, since that data has no severity labels of its own — one source of truth for "what counts as Severe AMS," not two.

xgb_ordinal.py

Day 5 — the selected model

Trained as a REGRESSOR on the continuous severity index, not a plain 5-class classifier.

1Regression, not classification
model = xgb.XGBRegressor(
    n_estimators=300, max_depth=5, learning_rate=0.05,
    objective="reg:squarederror",
    early_stopping_rounds=20, eval_metric="mae",
)
model.fit(X_train, y_train, sample_weight=sample_weight, eval_set=[(X_val, y_val)])
A prediction of 3.7 for a true HACE-risk (4) case is a small squared-error loss; a prediction of 0.2 is a big one. Plain multi-class classification would score both "Normal predicted, HACE true" and "Mild AMS predicted, Severe AMS true" identically — this throws that distinction away.
2Threshold tuning, and the Day 13 detour
UNDER_TRIAGE_PENALTY_WEIGHT = 1.0  # reverted here after Day 13 testing

def _asymmetric_tier_error(y_pred, y_true):
    error = y_pred - y_true
    weights = np.where(error < 0, UNDER_TRIAGE_PENALTY_WEIGHT, 1.0)
    return float(np.mean(np.abs(error) * weights))
Day 13 attempt: weight was raised to 3.0, then 1.5, to penalize under-triage more — both reduced the "45% of HAPE/HACE below the alert gate" figure, but both caused false alerts on genuinely Normal scenarios (10/10 test seeds at weight 3.0). Reverted to 1.0 (symmetric, identical to the original behavior) — verified byte-for-byte against the pre-Day-13 saved model.

Outputspo2_delta 0.3193 time_at_altitude_min 0.2227 spo2 0.1228 ascent_rate 0.1188 altitude 0.0584 temp 0.0538 hr 0.0433 spo2_trend_5min 0.0424 hr_trend_5min 0.0183

lstm_model.py

Day 6 — comparison model

A small 2-layer PyTorch LSTM, trained on raw 60-second windows, built to demonstrate the DL alternative honestly.

1Raw sequence input, not engineered features
LSTM_RAW_COLUMNS = ["spo2", "hr", "temp", "altitude"]  # NOT the trend features

class SeverityLSTM(nn.Module):
    def __init__(self, n_features, hidden_size=48, n_layers=2):
        self.lstm = nn.LSTM(input_size=n_features, hidden_size=hidden_size,
                             num_layers=n_layers, batch_first=True, dropout=0.2)
        self.head = nn.Sequential(nn.Linear(hidden_size, 32), nn.ReLU(),
                                   nn.Dropout(0.2), nn.Linear(32, N_TIERS))
Deliberately small — per the project's own instruction to keep this a comparison, not a bid for maximum performance. Classifies directly into 5 classes with cross-entropy (a genuinely different ordinal-handling strategy than XGBoost's regression).
2Result — and why it lost
OutputPrecision (macro): 0.403 Recall (macro): 0.408 F1 (macro): 0.397 Mean Abs Tier Error: 0.701 Under-triage rate: 0.203
Comparable F1 to XGBoost, but a clearly WORSE Mean Absolute Tier Error — XGBoost's structural ordinal-awareness (the regression target) measurably outperformed the LSTM's raw-sequence approach on this dataset size and shape. A real, evidence-based conclusion, not an assumption.

metrics.py

Day 4-7 shared infrastructure

Every model scored with literally the same code — this is what made the Day 13 finding even visible.

1Macro-averaging, and why it matters
precision_macro = precision_score(y_true, y_pred, average="macro", zero_division=0)
Macro-averaging gives every class EQUAL weight regardless of how common it is. A model that nails Normal (55% of the data) and completely ignores HACE risk (4%) would still score well on micro/weighted metrics — macro-averaging can't be fooled this way.
2Mean Absolute Tier Error + under-triage rate
mate = float(np.mean(np.abs(y_pred - y_true)))
under_triage_rate = float(np.mean(y_pred < y_true))
Under-triage (predicting too mild) is the clinically dangerous direction — tracked as its own explicit metric so it can't hide inside an aggregate accuracy number. This exact metric is what surfaced the Day 13 finding.

scenario_player.py — reuses the training-data generator

def _generate(self) -> None:
    rng = np.random.default_rng(self._seed)
    df = simulate_trajectory(subject_id=f"demo_{...}", tier=self._tier,
                              duration_minutes=self._duration_minutes, rng=rng)

buffer.py — Stage 2, validate + roll

VALID_RANGES = {"spo2": (0.0, 100.0), "hr": (20.0, 300.0),
                 "temp": (25.0, 45.0), "altitude": (-500.0, 9000.0)}

def add(self, reading) -> bool:
    for field, (lo, hi) in VALID_RANGES.items():
        value = reading.get(field)
        if value is None or not (lo <= value <= hi):
            self.rejected_count += 1
            return False
    self._readings.append(reading)
    return True
Verified: a synthetic -999% SpO2 glitch injected mid-stream during Day 13 testing was rejected cleanly, zero crash, buffer otherwise unaffected.

hysteresis.py

Day 11 — subject of Day 13's investigation

Two conditions, both required. Stateful across ticks by design.

1The full gate logic
def evaluate(self, severity_index, now=None):
    if severity_index >= self.alert_tier:
        self._consecutive_count += 1
    else:
        self._consecutive_count = 0  # any dip resets the streak

    streak_satisfied = self._consecutive_count >= self.consecutive_required
    cooldown_satisfied = (self._last_alert_time is None
        or (now - self._last_alert_time) >= self.cooldown_seconds)

    if streak_satisfied and cooldown_satisfied:
        self._last_alert_time = now
        return True
    return False
now is injectable specifically so tests can control time directly instead of sleeping in real time for 15 minutes to exercise the cooldown path.
2Verified: exactly one alert per episode
Output — sustained HACE-risk scenariototal ticks: 1800 last severity: HAPE risk alerts fired: 1 tick 559 Severe AMS sent=False (Telegram not configured in this test) ticks above Severe-AMS threshold after tick 559: 1228 but only 1 alert fired total -- cooldown correctly suppressed re-firing

Found by: actually timing a full scenario run, which took far longer than expected. Calling explain_severity() every tick means one Groq API call per second in a live 1Hz loop — impractical for cost, latency, and free-tier rate limits.

markdownConfidence: an honest, not over-claimed, proxy

XGBoost branch: measures how close the raw continuous prediction sits to the center of its bin vs. an edge — explicitly not a calibrated probability. LSTM branch: torch.softmax(logits) genuinely is a probability, since the LSTM is a real classifier with a softmax head. When this reaches the LLM prompt or dashboard, it should be presented honestly, not implying more precision than the underlying number has.
