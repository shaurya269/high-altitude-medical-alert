The models and techniques, in plain English

Read this section first — every module below refers back to these.

Ordinal classification

A classification problem where the categories have a meaningful ORDER. Here: Normal < Mild AMS < Severe AMS < HAPE risk < HACE risk. Being one tier off should count as a smaller mistake than being four tiers off — plain multi-class classification can't express that.

XGBoost, trained as a regressor

The selected model. Instead of classifying into 5 discrete categories, it's trained to predict the severity INDEX as a continuous number (0.0-4.0). Predicting 3.7 for a true 4 is a small loss; predicting 0.2 is a big one — the loss function itself understands tier ordering.

LSTM (comparison model)

A small recurrent neural network trained on raw 60-second vitals windows, testing whether a model can learn temporal patterns directly from a sequence, without a human hand-engineering a "trend" feature first. Built honestly, not built to lose — but it lost on the metric that matters.

Mean Absolute Tier Error (MATE)

The metric models are actually selected by: average |predicted tier − true tier|. Directly measures "how clinically costly are this model's mistakes," which plain accuracy can't.

Hysteresis gate

The logic deciding whether a classification actually triggers an alert: severity must stay at/above a threshold for 3 consecutive readings (any dip resets it) AND 15 minutes must have passed since the last alert.

DataSource interface

An abstract two-method contract (next_reading(), reset()) every reading source implements — this is what makes a future real-hardware phase a drop-in swap instead of a rewrite.

1The sigmoid onset curve

Symptoms ramp in gradually over minutes — never an instant jump — because a model trained on step-function data would learn to detect abrupt discontinuities, not the gradual real-world deterioration this system needs to catch.

def _smooth_ramp(n_samples, onset_fraction, rng):
    onset_start = int(n_samples * onset_fraction)
    t = np.arange(n_samples, dtype=float)
    remaining = max(n_samples - onset_start, 1)
    center = onset_start + remaining * 0.5
    width = max(remaining * 0.18, 1.0)
    ramp = 1.0 / (1.0 + np.exp(-(t - center) / width))
    ramp[t < onset_start] = 0.0
    return ramp
2Per-tier physiological profiles

Each tier has RANGES, not fixed numbers, so within-class variation is natural rather than every "Mild AMS" case looking identical.

TIER_PROFILES = {
    "Normal":     TierProfile((-1.5, 1.5),  (-5, 8),   (-0.2, 0.2), progressive=False),
    "Mild AMS":   TierProfile((4, 8),       (10, 20),  (-0.1, 0.4), progressive=False),
    "Severe AMS": TierProfile((8, 14),      (20, 35),  (0.0, 0.6),  progressive=False),
    "HAPE risk":  TierProfile((14, 22),     (28, 45),  (-0.1, 0.5), progressive=True),
    "HACE risk":  TierProfile((16, 26),     (32, 50),  (-0.1, 0.7), progressive=True),
}
Why "progressive": Mild/Severe AMS plateau after onset (sick but stable); HAPE/HACE risk keep worsening through the whole window (no recovery) — matching the clinical idea that these are decompensating states, per docs/lls_mapping.md.

3The GMT offset bug

6 of 15 subjects had their key_timestamp.txt altitude markers recorded exactly 8 hours ahead of their own vitals data.

data_start = pd.to_datetime(timestamps).min()

1The cascading thresholds
def classify_row(spo2_delta, hr, spo2_trend_5min):
    hr_elevation = hr - hr_normal_mid
    steep_negative_trend = spo2_trend_5min < -0.15

    if spo2_delta >= 16 or (spo2_delta >= 10 and steep_negative_trend):
        if spo2_delta >= 20 and hr_elevation >= 35:
            return SEVERITY_INDEX["HACE risk"]
        return SEVERITY_INDEX["HAPE risk"]
    if spo2_delta >= 8 or hr_elevation >= 20:
        return SEVERITY_INDEX["Severe AMS"]
    if spo2_delta >= 4 or hr_elevation >= 10:
        return SEVERITY_INDEX["Mild AMS"]
    return SEVERITY_INDEX["Normal"]

2Threshold tuning, and the Day 13 detour
UNDER_TRIAGE_PENALTY_WEIGHT = 1.0  # reverted here after Day 13 testing

def _asymmetric_tier_error(y_pred, y_true):
    error = y_pred - y_true
    weights = np.where(error < 0, UNDER_TRIAGE_PENALTY_WEIGHT, 1.0)
    return float(np.mean(np.abs(error) * weights))
Day 13 attempt: weight was raised to 3.0, then 1.5, to penalize under-triage more — both reduced the "45% of HAPE/HACE below the alert gate" figure, but both caused false alerts on genuinely Normal scenarios (10/10 test seeds at weight 3.0). Reverted to 1.0 (symmetric, identical to the original behavior) — verified byte-for-byte against the pre-Day-13 saved model.

metrics.py

Day 4-7 shared infrastructure

Every model scored with literally the same code — this is what made the Day 13 finding even visible.

1Macro-averaging, and why it matters
precision_macro = precision_score(y_true, y_pred, average="macro", zero_division=0)
Macro-averaging gives every class EQUAL weight regardless of how common it is. A model that nails Normal (55% of the data) and completely ignores HACE risk (4%) would still score well on micro/weighted metrics — macro-averaging can't be fooled this way.
2Mean Absolute Tier Error + under-triage rate
mate = float(np.mean(np.abs(y_pred - y_true)))
under_triage_rate = float(np.mean(y_pred < y_true))
Under-triage (predicting too mild) is the clinically dangerous direction — tracked as its own explicit metric so it can't hide inside an aggregate accuracy number. This exact metric is what surfaced the Day 13 finding.

buffer.py — Stage 2, validate + roll

VALID_RANGES = {"spo2": (0.0, 100.0), "hr": (20.0, 300.0),
                 "temp": (25.0, 45.0), "altitude": (-500.0, 9000.0)}

def add(self, reading) -> bool:
    for field, (lo, hi) in VALID_RANGES.items():
        value = reading.get(field)
        if value is None or not (lo <= value <= hi):
            self.rejected_count += 1
            return False
    self._readings.append(reading)
    return True

1The full gate logic
def evaluate(self, severity_index, now=None):
    if severity_index >= self.alert_tier:
        self._consecutive_count += 1
    else:
        self._consecutive_count = 0  # any dip resets the streak

    streak_satisfied = self._consecutive_count >= self.consecutive_required
    cooldown_satisfied = (self._last_alert_time is None
        or (now - self._last_alert_time) >= self.cooldown_seconds)

    if streak_satisfied and cooldown_satisfied:
        self._last_alert_time = now
        return True
    return False

markdownTierProfile ranges, and the "progressive" flag

Each tier has ranges, not fixed numbers, so sampling uniformly within a range gives natural within-class variation. progressive is the key clinical modeling decision: Mild/Severe AMS plateau after onset (sick but stable), while HAPE/HACE risk are progressive (keep worsening through the whole window, no plateau) — matching the clinical idea that these are decompensating, dangerous trajectories that don't self-stabilize.

Notice these ranges deliberately OVERLAP at the boundaries (Severe AMS tops out at 14, HAPE risk starts at 14; Severe AMS's HR band goes to 35, HAPE risk's starts at 28) — real physiology doesn't have hard cutoffs between adjacent illness tiers either, and a model that can't handle some ambiguity at tier boundaries would be learning a false certainty the data itself doesn't support. Each subject's actual value is drawn uniformly at random from within its tier's range (e.g. rng.uniform(8, 14) for a Severe AMS subject's spo2_delta target) — this is what makes two different "Severe AMS" subjects look like different people rather than clones of the same template patient.
markdownClass imbalance is intentional

TIER_PREVALENCE gives Normal 55%, down to HACE risk at 4%. Real populations at altitude are mostly fine — severe illness is genuinely rare. This imbalance must be real and handled (via class weighting in the models), not artificially balanced away, or the models would learn a false prior about how common HACE risk actually is.

ParameterMeaning
n_samplesTotal length of the trajectory in samples (duration_minutes × 60 at 1Hz) — the ramp array is exactly this long.

codeStride-downsampling vs. averaging — preserving real noise

OutputOriginal (100Hz) std: 2.93 Strided (1Hz) std: 2.81 <- preserves real per-sample noise Averaged (1Hz) std: 0.29 <- artificially smoothed, understates noise
Why stride, not average: our models need to learn to handle noisy readings, because that's what the real Arduino will actually produce. Averaging every 100 samples down to 1 would smooth out real sensor noise and make the models overconfident about clean signals.
Reading the standard deviations: a standard deviation (std) measures how spread-out a set of values is around its mean — the original 100Hz noisy signal has std=2.93 (values regularly deviate ~3 units from the mean by chance). strided = fake_100hz.iloc[::100] (Python's slice-step syntax, meaning "every 100th element starting from index 0") keeps std=2.81 — nearly identical to the original, because each kept sample is still one genuinely noisy reading, just fewer of them. averaged instead computes the MEAN of each consecutive 100-sample block (via groupby(np.arange(len) // 100) — integer division groups indices 0-99 together, 100-199 together, etc.) — averaging 100 independent noisy samples together mathematically shrinks the noise by a factor of √100=10, which is exactly why std drops to 0.29 (2.93 / 10 ≈ 0.29). That 10x reduction is the averaging artifact this cell exists to demonstrate and avoid.

temporal_split() parameter / ruleValueWhat it does
train_frac, val_frac0.70, 0.15 (from config.py)Within EACH tier's own sorted subject list, the first 70% of subjects (chronologically) go to train, the next 15% to val, and the remainder (also ~15%) to test.

markdownWhy split by whole subject, never by row

If split by row instead, a test-set row at minute 47 of some subject's trajectory could sit right next to a train-set row at minute 46 of the same subject — the model would implicitly be tested on data adjacent to what it trained on. That's leakage. Splitting on whole subjects closes this off completely.

06 — rule_baseline.py: the sanity-floor baseline

notebooks/06_rule_baseline_walkthrough.ipynb

This model must exist before XGBoost or the LSTM are trusted. If a sophisticated model can't clearly beat a handful of hand-written if/else rules, that's a red flag about features or labels, not evidence the ML approach is wrong.

markdownThe full cascading decision tree, parameter by parameter

This is the entire model. No training, no gradient descent, no learned weights — every threshold below is a literature-derived number from docs/lls_mapping.md, hand-typed into classify_row(). Reading it top to bottom as a clinician's checklist:

def classify_row(spo2_delta, hr, spo2_trend_5min):
    hr_elevation = hr - HR_NORMAL_MID          # HR_NORMAL_MID = 75 (midpoint of the 50-100bpm resting band)
    steep_negative_trend = spo2_trend_5min < -0.15   # % SpO2 lost per second, sustained

    if spo2_delta >= 16 or (spo2_delta >= 10 and steep_negative_trend):
        if spo2_delta >= 20 and hr_elevation >= 35:
            return "HACE risk"
        return "HAPE risk"
    if spo2_delta >= 8 or hr_elevation >= 20:
        return "Severe AMS"
    if spo2_delta >= 4 or hr_elevation >= 10:
        return "Mild AMS"
    return "Normal"
ParameterValueMeaning
spo2_deltafloat, %expected_spo2(altitude) − actual_spo2. Positive = worse than altitude-adjusted expectation. This is the single most important number in the whole rule tree — every threshold below is written in terms of it, never raw SpO2.
hr_elevationhr − 75How far above the population-normal resting midpoint (not the individual's own baseline — a hand-written rule has no memory of one specific patient) the current heart rate sits.

Lets the model flag a rapidly-worsening case before the absolute deviation alone would.
16, 10% deltaThe two ways into HAPE/HACE territory: either the deviation alone is extreme (≥16%), OR a smaller deviation (≥10%) combined with a steep negative trend — "early HAPE can desaturate fast," per the clinical mapping doc.
20 + 35% delta + bpmWithin the HAPE/HACE danger zone, escalating to HACE specifically requires BOTH an even more extreme deviation (≥20%) AND strongly elevated HR (≥35bpm over the 75bpm midpoint) — modeling HACE as the more decompensated end of the same spectrum, not a separate condition.
8, 20% delta / bpmSevere AMS cutoffs — either signal alone is sufficient (an or, not and).
4, 10% delta / bpmMild AMS cutoffs — the lowest tier above Normal.
Every branch is an if, checked in order from most-severe to least — the moment a condition is met, that tier is returned and nothing lower gets checked. This cascading structure is why the ordering of the checks matters as much as the threshold values themselves.

markdownConfidence: an honest, not over-claimed, proxy

XGBoost branch: measures how close the raw continuous prediction sits to the center of its bin vs. an edge — explicitly not a calibrated probability. LSTM branch: torch.softmax(logits) genuinely is a probability, since the LSTM is a real classifier with a softmax head. When this reaches the LLM prompt or dashboard, it should be presented honestly, not implying more precision than the underlying number has.

edges = [0.0] + list(thresholds) + [4.0]        # e.g. [0.0, 0.85, 2.0, 2.85, 4.0, 4.0]
lo, hi = edges[tier_index], edges[tier_index + 1]  # this prediction's bin boundaries
span = max(hi - lo, 1e-6)
center = (lo + hi) / 2
confidence = 1.0 - min(abs(continuous - center) / (span / 2), 1.0) * 0.5

Worked example for the row below (continuous prediction ~1.83, tier_index=2/Severe AMS, thresholds=[0.85, 2.0, 2.85, 4.0]): this tier's bin runs from 0.85 to 2.0, so span=1.15 and center=1.425. Distance from center: |1.83 − 1.425| = 0.405. Normalized: 0.405 / (1.15/2) = 0.405/0.575 ≈ 0.70. Confidence: 1.0 − min(0.70, 1.0) × 0.5 = 1.0 − 0.35 = 0.65. The formula is deliberately bounded between 0.5 (prediction sits right on a bin edge — least certain, but the model still "chose" this tier over its neighbor, so never drops below 0.5) and 1.0 (prediction sits exactly at the bin's center — most certain). It is NOT a calibrated probability like the LSTM's softmax output — it's a "how borderline is this" heuristic, honestly labeled as such rather than presented with false precision.
