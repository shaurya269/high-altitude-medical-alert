Chat Summary

This is the story of how the High-Altitude Medical Alert System got built, told in the order it actually happened — across several separate working sessions. It is not a tidied-up version of events: real bugs are described as they were found, fix attempts that failed are kept in (not quietly erased), and every non-obvious decision is paired with the reasoning given for it at the time. Read it top to bottom to understand not just what exists in the repo today, but why it looks the way it does.

6 working sessions 14-day build plan, fully complete 2 real bugs found + fixed in Harespod loading 2 fix attempts tried and reverted (Day 13) 78+ automated tests by the end

Session 1 — Kickoff

start of project

The user asked to read the CLAUDE.md file and the three architecture diagrams already sitting in the (otherwise empty) project folder, understand the intended system, and start building — asking questions if anything was unclear.

What existed before any code was written

The project folder contained exactly four files: CLAUDE.md (the full project brief) and three static HTML architecture diagrams (01_system_architecture.html, 02_project_phases.html, 03_data_flow_diagram.html). No source code, no data, no git repository yet.

Reading CLAUDE.md in full established the shape of the whole project before a single line of code was written:

  • What it is: a sensor-based early-warning prototype for high-altitude illness — AMS (Acute Mountain Sickness), HAPE (High-Altitude Pulmonary Edema), and HACE (High-Altitude Cerebral Edema) — combining an ML severity classifier, an LLM interpretation/chat layer, and a Telegram alert bot.
  • Explicit current scope: software-only "Demo Mode." No physical hardware exists or would be built in this phase — everything runs on synthetic and replayed data behind a swappable interface, so a real Arduino could be dropped in later with zero changes to the rest of the pipeline.
  • The 14-day build plan: Days 1-7 (data + ML foundation), Days 8-14 (integration, LLM, alerts, dashboard, testing, docs) — laid out day-by-day in 02_project_phases.html.
  • Non-negotiable guardrails: the LLM must never diagnose, override the ML classification, give dosing advice, or discourage seeking real medical help.
Four clarifying questions were asked before writing any code:
  1. The Harespod dataset (the real sensor data CLAUDE.md names as the primary source) requires a manual browser download from Figshare — should the build wait for it, or proceed synthetic-first with a ready adapter?
  2. Are the Groq (LLM) and Telegram API keys available now, or should those layers be built stub-first?
  3. How should the 14-day plan be paced — all at once, one day at a time, or in week-sized chunks with check-ins?
  4. Should the project be placed under git, and should a remote be created?

The user chose the recommended option on all four: synthetic-first with a ready Harespod adapter, graceful degradation for both API keys (build now, wire in real keys whenever available), Days 1-7 as one continuous unit with a check-in before Week 2, and local git only, no remote yet.

Repo scaffold, Day 1-2

session 1

Built the target repo structure exactly as CLAUDE.md specified, then the synthetic data generator.

What got built

  • src/config.py — every shared constant (severity tiers, clinical thresholds, hysteresis config, split fractions) in one place, so nothing downstream invents its own copy of "what counts as Severe AMS."
  • src/data/harespod_loader.py — written before the real data was downloaded, deliberately, against the dataset's documented schema. Designed so it could later be pointed at real files with no change to its output contract.
  • src/data/synth_data.py — the synthetic vitals generator. Produces 400 simulated subjects across the 5 severity tiers, each with a gradual sigmoid onset (not an instant jump) because a model trained on step-function data would learn to detect abrupt jumps, not the gradual real-world deterioration this system needs to catch.
  • docs/lls_mapping.md — the written clinical rationale mapping the Lake Louise Score (a symptom questionnaire, not a sensor reading) to sensor patterns per tier. This became the single source of truth every rule-based threshold in the codebase traces back to.
Why write the Harespod loader before downloading Harespod: the user's chosen "synthetic-first, adapter ready" plan meant Days 2-7 shouldn't block on a manual Figshare download. Writing the loader early, against the documented (not yet verified) schema, meant real data could be dropped in later purely as a data-availability event, not a code-design event.

The stratified-split bug

Day 3

The first real bug of the project, caught before it could quietly corrupt every model trained afterward.

The bug: the original feature_engineering.py split subjects into train/val/test by sorting all 120 synthetic subjects together and cutting 70/15/15 chronologically. With only ~5 subjects in the rarest tier (HACE risk), a single unlucky ordering put every HACE-risk subject into the training set and zero into validation or test. This wasn't a coding typo — it ran without error and produced a plausible-looking split. It would have silently made every reported metric for the most dangerous tier meaningless.
The fix: the split logic was rewritten to stratify by severity tier first, then apply the same chronological 70/15/15 cut within each tier's own subject list. This still respects "never randomly shuffle time-series data" (each tier's own subjects stay time-ordered) while guaranteeing every tier appears in every split. The subject count was also raised from 120 to 400 so each tier had enough subjects to split meaningfully.

This became tests/test_pipeline.py::test_temporal_split_no_subject_overlap — a permanent regression test guarding against this exact failure mode recurring.

Days 4-7 — Baseline, XGBoost, LSTM

session 1

Three severity classifiers, built in the order CLAUDE.md required (baseline first, always) and compared on identical held-out data.

Day 4 — Rule-based baseline

src/models/rule_baseline.py encodes the clinical thresholds from docs/lls_mapping.md directly as if/else logic — no learned parameters. This exists specifically as a floor: if a sophisticated model can't clearly beat a handful of hand-written rules, that signals a problem with the features or labels, not evidence the ML approach doesn't work.

Day 5 — XGBoost ordinal classifier

Trained as a regressor on the severity index as a continuous number (0.0-4.0), not a plain 5-class classifier — this is what makes the model ordinal-aware: predicting 3.7 for a true HACE-risk (4) case is a small loss, predicting 0.2 is a big one, whereas plain multi-class classification would score both mistakes identically. Continuous output is then converted to a discrete tier via tuned threshold cut-points.

Day 6 — LSTM comparison model

A small 2-layer PyTorch LSTM trained on raw 60-second vitals windows (not the hand-engineered trend features XGBoost sees) — built specifically to demonstrate the deep-learning alternative and let the two approaches be compared honestly, per CLAUDE.md's explicit "don't build a model zoo, but do build this one comparison" instruction.

Session 2 — Teaching notebooks

separate session

The user came back and asked: convert every Days-1-7 Python file into notebook format with the same detailed line-by-line explanations, and asked why notebooks/ only had one file when src/ had so many.

The actual question, answered directly

src/ is the production pipeline: one job per file, imported by other files, the code that actually runs. notebooks/ is a separate, parallel teaching layer — one notebook per module, meant to be read and re-run interactively with the reasoning spelled out. Only one notebook existed because Days 1-7 moved fast under the user's "build straight through" pacing choice; the 1:1 notebook coverage hadn't been built yet.

Before building 8 notebooks' worth of content, one clarifying question was asked: should each notebook import and call the real src/ functions (staying accurate as the code evolves), or contain the full code copied inline (fully self-contained, but a second copy that can drift)? The user chose importing from src/.

What got built — 9 new notebooks, one per module

02_config_walkthrough, 03_synth_data_walkthrough, 04_harespod_loader_walkthrough, 05_feature_engineering_walkthrough, 06_rule_baseline_walkthrough, 07_metrics_walkthrough, 08_xgb_ordinal_walkthrough, 09_lstm_model_walkthrough, 10_predict_severity_walkthrough — each with real code cells, markdown explaining every non-obvious choice, and actually-executed outputs.

A real bug found while executing every notebook end to end: a .std().round() call failed with AttributeError: 'float' object has no attribute 'round'. In this environment's pandas 3.0, Series.std() returns a plain Python float rather than numpy.float64, which has no .round() method. Fixed by swapping to the builtin round() function. This was only caught because every notebook was actually run, not just written and assumed correct.

Harespod: inspecting the real download

session 3

The loader written back in Session 1 was speculative — written against Harespod's documented schema before the files existed. Now the real archive could be inspected directly.

What the real files actually looked like

15 usable subjects (not the initially-assumed count), in a Data_Cons/ folder, with per-subject CSVs for heart rate, SpO2 saturation, pulse rate, and two 100Hz waveform files. Critically, the column names in the raw CSVs were unlabeled numbers — the real mapping (spv = SpO2 Sat, not the raw spo waveform file that superficially looked like it could be SpO2) was only confirmed by reading the actual BerryMed PM6100 device driver source code shipped alongside the data.

Bug 1 — implausible rescale: Harespod's signals are min-max normalized to [0,1] per subject, with the true original scale unrecoverable. The first rescale attempt mapped onto the device's documented raw collection range (SpO2/pulse 0-100, heart rate 0-250bpm) — this produced a subject with a mean resting heart rate of 174bpm, clearly wrong for someone at rest. Fixed by rescaling onto a physiologically-plausible range instead (SpO2 70-100%, HR 40-160bpm) — still an approximation, but one that produces numbers a real pulse oximeter would plausibly report.
Bug 2 — an 8-hour GMT offset: 6 of the 15 subjects had their key_timestamp.txt altitude markers recorded exactly 8 hours ahead of their vitals data's own timestamps — a mismatch the file's own header comments warned about ("device record time may be GMT... 8H different from local time") but which the original loader didn't account for. Unfixed, this would have silently produced a constant altitude for the entire recording instead of a real ascent profile, for those 6 subjects. Fixed by detecting the offset per-subject (comparing the first marker to the data's own start time) and correcting it before interpolating.
Bug 3 — two per-subject format exceptions: subject 314c's first altitude marker was labeled "Start to Rec" instead of a numeric altitude (handled as meaning the same 1500m first stage); subject 328a's protocol never reached the final 4000m stage, with its marker literally reading "Did not rise to this altitude" — handled by dropping that marker rather than fabricating a fake timestamp.

All three fixes are documented directly in harespod_loader.py's own docstrings, not just in this summary — so anyone reading the code later sees the reasoning without needing this document.

The pilot-altitude-dataset detour

session 3

A real example of a promising lead that was investigated thoroughly and correctly ruled out — not silently abandoned, not forced to fit anyway.

Why a second dataset was even considered

Harespod's rescale ambiguity prompted a search for a better real dataset. A newly-published "High-Altitude Pilot Physiological Monitoring Dataset" (2026, Figshare) looked promising: real absolute units confirmed by inspecting its raw CSVs directly (SpO2 88-100%, HR 43-179bpm — genuinely physiological numbers, no rescaling needed), a higher and more clinically-relevant altitude range (4500-7500m vs Harespod's 1500-4000m), and more subjects (20 vs 15). The user approved downloading and integrating it.

The disqualifying finding: after building a loader and running the labeling pipeline against it, the results were physiologically backwards — a healthy 98% SpO2 reading at 7500m was being flagged as severely abnormal, because the project's expected_spo2() reference curve assumes ambient air, where 7500m would predict ~75% SpO2. Investigating further (using the dataset's own O2/N2/CO2 gas-composition columns, which had been loaded but not yet used) revealed the pilots were breathing oxygen-enriched air throughout (~40-45% O2, vs ~21% in normal atmosphere) — a fundamentally different physiological scenario than the ambient-air hypoxia this whole project models.

Before concluding, Harespod itself was double-checked against the same question (in case both real datasets turned out to be oxygen-enriched) — its own paper's Methods section confirmed ambient air only, with real oxygen used solely as an emergency intervention. A broader web search was also run to check whether any better real, ambient-air, publicly-downloadable dataset existed at all — none did.

Final decision: the pilot dataset stays loaded (src/data/pilot_altitude_loader.py) and available for exploration, but is excluded from severity labeling — rule-labeling an oxygen-enriched dataset with ambient-air thresholds would have actively mislabeled it, not just approximated it.

The train-only merge decision

session 3

A genuine circularity risk was caught before it could quietly invalidate every future model comparison.

Neither real dataset comes with severity labels, so both had to be labeled post-hoc using the same rule-based thresholds rule_baseline.py uses as a model. If those rule-labeled rows ended up in the validation or test split, evaluating the rule-based baseline against them would be circular — it would trivially "predict" labels it generated itself, making the whole three-way model comparison meaningless for real-data rows.

Decision (user-approved, with the alternative explicitly noted for later): real, rule-labeled data is merged into the training split only. Validation and test stay 100% synthetic, whose labels come from the generator's own tier-driven simulation, never from classify_row() — so evaluating the rule baseline against them is never circular. A documented alternative (splitting real data across all three sets, and having the comparison function score the rule baseline only on synthetic rows) was written into the code as a note for later, not implemented.

Retraining XGBoost and the LSTM on the blended dataset showed both models improved somewhat from the added real signal — XGBoost remained the selected model.

Week 2 begins

The user asked to continue with the next phase of the 14-day plan. This session built Days 8 through 12 in one continuous run.

An abstract DataSource interface (just two methods: .next_reading() and .reset()) with three concrete Demo Mode implementations: a scenario player (reusing the Day 2 synthetic trajectory simulator directly), a manual slider override, and a Harespod replay source. Day 9 — LLM interpretation, chat, guardrails

session 4

One shared, guardrailed system prompt behind three functions: plain-language severity explanation, live chat, and structured-JSON alert content generation.

The system prompt encodes all four of CLAUDE.md's non-negotiable rules explicitly (never diagnose, never override the ML classification, never give dosing advice, never discourage seeking real help) rather than relying on the model's own implicit judgment.

Verified, not assumed: the guardrails were tested directly with a real adversarial prompt — a user message insisting they felt fine despite an elevated classification, and directly asking for a specific medication dose. The model correctly refused to override the classification and correctly refused the dosing request, redirecting to "seek real medical attention" both times.

A templated, non-LLM fallback (matching the same guardrails, just hand-written instead of model-generated) activates automatically when no Groq key is present, or when a live call fails — which was actually observed later in testing, when Groq's free-tier daily token limit was hit from heavy same-day testing, and the fallback engaged cleanly instead of crashing.

Day 10 — Telegram alerts

session 4

One shared alert-message format, a local JSONL log as both the offline fallback and a permanent record, and two real messages sent and confirmed delivered during testing.

Day 11 — full pipeline integration

session 4

The hysteresis gate and the MedicalAlertPipeline class that wires every prior piece together into one .tick() call.

A real design gap found while testing, not after shipping: the first version called the LLM's explain_severity() on every single tick. In a live 1Hz loop, that means one Groq API call per second — impractical for cost, latency, and free-tier rate limits. This was caught by actually timing a full scenario run, which took far longer than expected.
Fix: the explanation is now cached and only regenerated when the severity tier changes, not on every tick. "Stage 6A - ALWAYS" in the data flow diagram was clarified to mean "always eligible, independent of the hysteresis gate" rather than "literally every tick regardless of cost."

The fixed pipeline was verified against a sustained HACE-risk scenario (fires exactly one alert, correctly de-duplicated by the 15-minute cooldown despite hundreds of consecutive elevated readings) and a Normal scenario (fires zero alerts).

Day 12 — Streamlit dashboard

session 4

The Demo Mode control panel, live vitals/severity charts, a chat tab, and an alert log tab — verified in an actual running browser, not just by reading the code.

The app was launched for real and driven with Playwright (a headless browser automation tool) to click through every mode — scenario player, manual sliders, Harespod replay — and take screenshots at each step, checking the browser's console for JavaScript errors along the way.

A moment that looked like a bug but wasn't:
After only 5 "Step forward" clicks, the severity readout still showed the empty "start a Demo Mode source" placeholder text, and the charts showed empty "Infinite extent" console warnings. This looked broken. Stepping forward far enough to cross the model's minimum-history requirement (60 readings) resolved it completely — the severity readout, vitals snapshot, LLM explanation, and both charts all populated correctly. This was genuinely correct behavior (the model shouldn't classify off too little history), not a bug, and it became a permanent regression test in the automated suite (streamlit.testing.v1.AppTest) rather than something left to rediscover by accident later.

Session 5 — Day 13: testing & a real safety finding

the most important investigation

Continued from the previous session. All 15 real Harespod recordings were replayed through the complete pipeline (zero exceptions, zero rejected readings, correctly de-duplicated to one alert each), and six hand-crafted edge cases were tested directly.

Edge cases tested

  • An instantaneous step-function drop (not the gradual onset the model was trained on) — handled correctly.
  • Readings oscillating right at the alert-tier boundary — correctly never fired (a single dip resets the streak).
  • Exactly one reading short of the consecutive-streak requirement — correctly never fired.
  • Exactly the required streak length — correctly fired.
  • A physiologically-impossible sensor glitch (-999% SpO2) — correctly rejected by the buffer, no crash.
  • An empty/already-exhausted data source — correctly reported as exhausted, no crash.
The real finding: on the held-out (pure synthetic) test set, 45% of true HAPE-risk/HACE-risk readings received an XGBoost prediction below the hysteresis gate's alert-eligible tier (Severe AMS). Even with hysteresis working perfectly, the system would never even attempt a Telegram alert for nearly half of the most dangerous cases — because the classification feeding into the gate was itself under-confident on the rarest tiers, not because of any hysteresis-gate bug.

Fix attempt 1: asymmetric threshold tuning

tried and reverted

The XGBoost threshold-tuning search was modified to penalize under-triage errors (predicting too mild) more heavily than over-triage errors of the same size — first at a 3x penalty weight.

Penalty weightHAPE/HACE below alert gateNormal scenarios falsely alerting
1.0 (original, symmetric)45.0%0 / 10 seeds
3.026.8%10 / 10 seeds
1.533.3%confirmed systematic by seed 3, stopped there
Why it failed: biasing the threshold that separates Normal from Severe AMS pushes ordinary sensor noise on a genuinely Normal trajectory across that same line often enough to satisfy the 3-consecutive-reading hysteresis requirement. This isn't a tunable edge case — it's a direct, structural consequence of moving the boundary the gate depends on.

Reverted cleanly to weight 1.0. Verified on disk that the saved model thresholds and comparison numbers matched the pre-Day-13 baseline exactly, and that the specific test that had failed (test_normal_scenario_never_fires_an_alert) passed again, along with the full 67-test suite.

Fix attempt 2: lower the gate to Mild AMS

tried and reverted

A different approach: leave the model's own classification thresholds untouched, and instead lower HYSTERESIS_ALERT_TIER from Severe AMS to Mild AMS — reasoning that this doesn't distort the model's calibration, just changes what the gate watches for.

This substantially improved coverage: only 9.7% of true HAPE/HACE readings now fell below the new, lower gate (down from 45%). But checking the single-reading false-positive rate first (38% of true-Normal readings already predict at/above Mild AMS individually) was a warning sign, and a live Normal-scenario test confirmed it: the very first seed tested fired a false alert, matching the same systematic pattern as attempt 1.

Why it failed: this model was simply never trained/tuned to separate Normal from Mild AMS as tightly as it separates Normal from Severe AMS — so a large fraction of ordinary Normal-scenario noise already sits at or above Mild AMS, easily sustaining a 3-in-a-row streak.

Reverted back to Severe AMS. Re-verified: the full test suite passed, and both the false-alarm test and the sustained-danger-fires-an-alert test were explicitly re-run and confirmed individually, not just inferred from the aggregate pass count.

Why both attempts failed, and what actually shipped

conclusion

Both fix attempts hit the same underlying wall: this specific XGBoost model's calibration doesn't currently support catching more true danger without also catching more false alarms, at any tier boundary tried. The system ships with the original, well-tested configuration — Severe AMS gate, symmetric threshold tuning — which is honestly biased toward fewer false alarms at the cost of missing some true elevated cases. This is documented as a known, real limitation in docs/lls_mapping.md and the README, with the two failed attempts described in enough detail that anyone revisiting this later doesn't have to rediscover the same dead ends. Real fixes that would need actual new work (not attempted here) are listed too: a model specifically trained to separate Normal from everything else more sharply, a second independent signal required to agree before alerting, or more real (non-synthetic) training data at exactly the Normal/Mild-AMS boundary where both attempts' false alarms concentrated.
